# Bybit P2P: ссылки, API и открытие в приложении

Краткий конспект по **официальной** документации Bybit (на момент проверки). Цель — понять, можно ли из `itemId`/`id` объявления собрать ссылку, которая **гарантированно** откроет **детальную страницу объявления** в приложении.

## Термины

| Что | Поле в API | Комментарий |
|-----|------------|-------------|
| **Объявление (advertisement / item)** | `id` в ответе листинга; в телах запросов часто `itemId` | То, что возвращает `POST /v5/p2p/item/online` — до создания сделки |
| **Ордер / сделка P2P (order)** | отдельный идентификатор сделки | Появляется после принятия объявления контрагентом |

В разговорной речи «ордер» часто путают с объявлением; для кнопки «Купить» в боте речь именно об **объявлении**, пока пользователь ещё не создал сделку.

## Что описывает публичный P2P API

Источники:

- [P2P Authentication / обзор](https://bybit-exchange.github.io/docs/p2p/guide)
- [Get Online Ads](https://bybit-exchange.github.io/docs/p2p/ad/online-ad-list) — листинг объявлений
- [Get My Ad Details](https://bybit-exchange.github.io/docs/p2p/ad/ad-detail) — `POST /v5/p2p/item/info`, параметр `itemId`

В этих разделах документируются **REST-эндпоинты и поля ответов**. Там **нет** спецификации:

- HTTPS URL вида «открой это объявление в браузере / приложении»;
- схемы `bybitapp://…` для перехода на **экран объявления** по `itemId`;
- генерации «share»-ссылки для третьей стороны по одному только `itemId`.

Итог: из официального API **можно взять идентификатор объявления**, но **нельзя по документации** вывести однозначный канонический deep link на его карточку в приложении.

## Что описывает Help Center (шаринг объявления)

Источник: [FAQ — P2P Advertisers](https://www.bybit.com/en/help-center/article/FAQ-P2P-Verified-Advertisers-on-Bybit) (раздел про Share).

Факты из статьи:

- Поделиться объявлением можно через **QR или URL** из потока **My Ads → Share**.
- Одну и ту же ссылку можно отправить нескольким контрагентам.
- Ссылка и QR **истекают через 30 минут**.
- Речь про объявление рекламодателя в **активном** статусе.

Это подтверждает модель **краткоживущего токена шаринга**, который генерирует продукт Bybit, а не «вечный» URL из публичного API для произвольного `itemId`.

## Неофициальные / комьюнити упоминания схем приложения

В открытых источниках встречаются примеры вида:

- `bybitapp://open/route?targetUrl=<URL-encoded https>` — обёртка: приложение открывает переданный **веб**-URL (часто во встроенном WebView).
- `bybitapp://open/fiat_otc_order_detail?orderId=…` — в названии и параметре фигурирует **order** (сделка), не идентификатор объявления из листинга.

Эти форматы **не приведены** в проверенных фрагментах официальной P2P API-документации как поддерживаемый контракт для интеграторов. Использовать их можно только как эвристику с риском смены поведения приложения.

## Почему `https://www.bybit.com/...?itemId=…` может открывать список

Фронтенд Bybit — SPA; какие query-параметры реально монтируют экран **детали объявления**, не зафиксированы в P2P API docs. Поэтому:

- Telegram WebView может не отдавать ссылку системе как Universal Link;
- даже корректный для сайта URL может игнорировать часть параметров в конкретной сборке приложения/региона.

## Настройки ссылок в этом боте (`.env`)

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `BYBIT_P2P_LINK_MODE` | `direct` | `direct` — одна ссылка на `www` + локаль; `inapp` — обёртка `app.bybit.com/inapp` |
| `BYBIT_P2P_WEB_HOST` | `www.bybit.com` | Домен без схемы; при необходимости — `www.bybitglobal.com` |
| `BYBIT_P2P_WEB_LOCALE` | `en-US` | Первый сегмент пути после хоста (`en`, `ru-RU`, …) |

Почему по умолчанию **direct**: промежуточная страница `inapp` часто открывается во встроенном WebView Telegram и показывает общий список P2P, не подхватывая deep route объявления.

## Практические выводы для бота

1. **Гарантированного** способа из данных `GET online ads` собрать ссылку «всегда открывает карточку этого объявления в приложении» в официальной документации **нет**.
2. Единственный явно описанный продуктовый механизм точечного открытия для контрагента — **Share URL** из кабинета рекламодателя (**срок жизни 30 минут**), его публичное API для чужих объявлений не описывает.
3. Разумная стратегия для мониторингового бота:
   - использовать **HTTPS URL пары** с параметрами в духе `itemId` / `adNo` (как сейчас в коде) как лучшее приближение для сайта;
   - обёртку `https://app.bybit.com/inapp` сохранять там, где нужен обход блокировок и попытка вызвать приложение;
   - в `bybitapp://open/route?targetUrl=…` передавать **percent-encoded** полный HTTPS URL, иначе символ `&` из query обрежет `targetUrl` при разборе deep link;
   - в UI/документации предупреждать: при необходимости открыть **во внешнем браузере** или из приложения Bybit.

Если Bybit позже добавит в API поле вроде `shareUrl`/`deeplink` для объявления или опубликует схему deep links для `itemId`, логику стоит обновить под этот контракт.
